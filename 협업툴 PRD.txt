아래는 기존 PRD를 바탕으로 선택한 13개 기능을 모두 반영한 통합 PRD v1.0입니다.

기존의 단순하고 직관적인 협업툴이라는 방향을 유지하면서 개발자가 별도 해석 없이 구현할 수 있도록 기능 요구사항, 권한, 데이터 구조, 예외 처리, 완료 기준까지 구체화했습니다.

# PRD v1.0 — 간단하고 직관적인 팀 협업 칸반보드

**프로젝트 유형:** 웹 기반 팀 업무 관리 및 협업 서비스\
**대상 사용자:** 6\~30명 규모의 사내 팀\
**핵심 콘셉트:** Jira보다 가볍고, 엑셀보다 직관적인 실시간 업무 공유 도구\
**우선 플랫폼:** PC 웹 / 모바일 반응형 웹\
**개발 범위:** MVP 1차 버전

---

## 1. 프로젝트 개요

### 1.1 제품 목표

팀원들이 수행 중인 업무를 하나의 칸반보드에서 등록, 배정, 조회, 수정하고 실시간으로 공유할 수 있는 웹 기반 협업툴을 개발한다.

복잡한 프로젝트 관리 기능보다 업무의 가시성, 간편한 조작, 빠른 정보 공유에 집중한다.

### 1.2 문제 정의

**① 흩어진 업무 관리**

현재 엑셀, 구글시트, 카카오톡, 메신저 등 여러 도구에서 업무를 관리하고 있어 관련 정보가 분산되어 있다.

**② 반복되는 수작업**

업무 진행 현황을 확인하거나 정리하는 데 약 10분이 소요되며, 이러한 작업이 반복된다.

**③ 업무 상황 파악의 어려움**

팀원별 담당 업무, 진행 상태, 완료 여부, 문제 발생 현황을 한눈에 확인하기 어렵다.

**④ 실시간 공유 부족**

담당자 또는 업무 상태가 변경되어도 다른 팀원이 즉시 확인하기 어려워 커뮤니케이션 비용이 발생한다.

### 1.3 성공 목표

- 업무 현황을 하나의 화면에서 확인할 수 있다.
- 팀원별 담당 업무 및 마감일을 쉽게 파악할 수 있다.
- 업무 상태를 드래그 앤 드롭으로 변경할 수 있다.
- 다른 팀원의 변경 내용이 새로고침 없이 반영된다.
- 업무 등록부터 담당자 배정까지 간단한 조작으로 완료할 수 있다.
- PC와 모바일에서 모두 사용할 수 있다.

## 2. 타깃 사용자

### 2.1 핵심 사용자

사내 팀 구성원 6\~30명.

- 개발 지식 없이 사용 가능해야 한다.
- 엑셀, 메신저 기반 업무 공유에 익숙하다.
- 자신이 맡은 업무와 팀 전체 진행 상황을 빠르게 확인하고 싶어 한다.

### 2.2 사용자 역할

**관리자 (Admin)**

- 팀 및 프로젝트 보드 생성·관리
- 팀원 초대 및 관리
- 모든 업무 조회·등록·수정
- 업무 삭제 및 복구
- 완료 업무 보관 및 복원

**일반 팀원 (Member)**

- 자신이 참여한 보드 조회
- 업무 등록 및 수정
- 담당자 배정 및 변경
- 업무 상태 변경
- 업무 검색 및 필터
- 자신의 업무 조회

관리자는 초기 팀 생성자로 지정한다.

## 3. 서비스 구조

서비스는 다음 계층으로 구성한다.

**워크스페이스 → 프로젝트 보드 → 업무 카드**

### 3.1 워크스페이스

팀원들이 함께 사용하는 최상위 협업 공간이다.

MVP에서는 하나의 사용자가 하나의 워크스페이스에 소속되는 구조를 기본으로 한다.

### 3.2 프로젝트 보드

워크스페이스 안에 여러 개의 보드를 생성할 수 있다.

예시:

- 공통 업무
- 신규 서비스 개발
- 운영 및 유지보수
- 내부 개선 과제

보드마다 업무 카드를 독립적으로 관리한다.

### 3.3 업무 상태

기본 칸반보드는 다음 네 가지 상태로 구성한다.

| 상태          | 의미                      |
| ----------- | ----------------------- |
| To Do       | 진행 예정 업무                |
| In Progress | 현재 진행 중인 업무             |
| Done        | 완료된 업무                  |
| Issue       | 문제가 발생했거나 별도 대응이 필요한 업무 |

MVP에서는 Issue를 독립적인 업무 상태로 관리한다.

각 업무는 한 번에 하나의 상태만 가진다.

상태 변경은 드래그 앤 드롭 또는 상세 화면의 상태 선택으로 처리한다.

Issue에서 다른 상태로 이동할 수 있으며, 해당 변경 내용은 이력에 기록한다.

**기본 정책:** 업무 상태는 관리자가 별도로 정의하지 않으며 네 가지로 고정한다.

## 4. 핵심 기능 요구사항

### FR-01. 로그인 및 사용자 인증

**목적:** 사용자별 업무 관리 및 접근 권한 구분.

**요구사항**

- 이메일 및 비밀번호 기반 회원가입과 로그인을 제공한다.
- 로그아웃 기능을 제공한다.
- 로그인 상태를 유지할 수 있다.
- 비밀번호 재설정 기능을 제공한다.
- 로그인하지 않은 사용자는 내부 보드에 접근할 수 없다.
- 로그인 이후 기본 대시보드로 이동한다.
- 사용자 정보는 고유 ID로 관리한다.

**예외 처리**

- 잘못된 비밀번호 입력 시 오류 메시지를 표시한다.
- 존재하지 않는 계정은 로그인할 수 없다.
- 인증 세션이 만료되면 재로그인을 요청한다.

### FR-02. 팀원 초대

**목적:** 같은 팀 구성원들이 공동 작업할 수 있도록 한다.

**요구사항**

- 관리자는 이메일 주소로 팀원을 초대할 수 있다.
- 초대 대상의 이메일을 등록한다.
- 초대 링크를 생성하여 복사할 수 있다.
- 초대 링크는 해당 이메일 계정으로 로그인한 사용자만 수락할 수 있다.
- 초대 상태를 대기, 수락, 만료, 취소로 관리한다.
- 관리자는 대기 중인 초대를 취소할 수 있다.
- 초대받은 사용자는 수락 후 워크스페이스에 참여한다.
- 초대 링크는 기본 7일 후 만료된다.

**정책**

- 실제 초대 이메일 발송은 MVP 범위에서 제외한다.
- 기존 등록 계정은 초대 수락 후 참여한다.
- 신규 사용자는 회원가입 후 초대를 수락한다.
- 중복 초대 시 안내 메시지를 표시한다.

### FR-03. 보드 관리

**목적:** 프로젝트 또는 업무 성격별로 업무를 분리한다.

**요구사항**

- 관리자는 보드를 생성, 수정, 삭제할 수 있다.
- 보드에는 이름과 설명을 등록할 수 있다.
- 보드 목록에서 원하는 보드를 선택할 수 있다.
- 보드마다 독립적인 업무 목록을 관리한다.
- 보드별 참여자를 지정할 수 있다.
- 참여자만 해당 보드에 접근할 수 있다.
- 보드 생성 시 네 가지 기본 상태를 자동 생성한다.

**삭제 정책**

- 보드 삭제는 소속 업무에 영향을 주므로 확인 절차를 제공한다.
- MVP에서 보드 삭제는 소프트 삭제 방식으로 처리한다.
- 삭제된 보드와 소속 업무는 일반 화면에 노출하지 않는다.
- 관리자는 보드를 복구할 수 있다.

### FR-04. 칸반보드 조회 및 드래그 앤 드롭

**목적:** 업무 진행 상황을 시각적으로 확인하고 직관적으로 변경한다.

**요구사항**

- 기본 상태 4개를 열로 표시한다.
- 업무를 사각형 카드 형태로 표시한다.
- 카드를 다른 열로 드래그하면 상태가 변경된다.
- 같은 열 내부에서도 카드 순서를 변경할 수 있다.
- 변경된 상태와 순서는 데이터베이스에 저장한다.
- 변경 성공 시 다른 사용자 화면에도 반영한다.
- 저장 실패 시 이전 위치로 복구하고 오류 메시지를 표시한다.
- 카드 클릭 시 업무 상세 화면을 연다.

**카드 표시 정보**

- 업무 제목
- 담당자
- 완료기한
- 우선순위
- 업무 상태를 구분할 수 있는 시각적 요소
- 기한 초과 여부

**모바일 정책**

- 상태별 탭 또는 가로 스와이프 방식으로 열을 탐색한다.
- 터치 기반 드래그 앤 드롭을 지원한다.
- 드래그가 어려운 환경에서도 상세 화면에서 상태를 변경할 수 있다.

### FR-05. 업무 등록

**목적:** 새로운 업무를 빠르게 생성하고 공유한다.

**입력 항목**

| 항목    | 필수 | 내용               |
| ----- | -- | ---------------- |
| 제목    | 필수 | 업무명, 최대 150자     |
| 상세 설명 | 선택 | 업무 내용, 최대 5,000자 |
| 담당자   | 선택 | 보드 참여자 중 1명      |
| 완료기한  | 선택 | 날짜               |
| 우선순위  | 필수 | 높음, 보통, 낮음       |
| 상태    | 필수 | 기본값 To Do        |
| 보드    | 필수 | 업무가 소속되는 프로젝트    |

**요구사항**

- 신규 업무 생성 버튼을 제공한다.
- 등록 완료 시 해당 보드에 카드가 표시된다.
- 업무별 고유 ID를 부여한다.
- 등록자와 등록일시를 자동 저장한다.
- 담당자 미지정 상태도 허용한다.
- 우선순위 기본값은 보통으로 지정한다.

### FR-06. 업무 상세 화면

**목적:** 업무 내용을 확인하고 수정한다.

**요구사항**

- 카드 클릭 시 상세 화면을 표시한다.
- 상세 화면은 모달 또는 사이드 패널로 구현한다.
- 제목, 설명, 담당자, 완료기한, 우선순위, 상태를 수정할 수 있다.
- 생성일시, 수정일시, 등록자를 확인할 수 있다.
- 변경 이력을 확인할 수 있다.
- 저장 성공 시 카드와 상세 화면을 동기화한다.
- 저장하지 않은 변경이 있을 때 화면을 닫으면 확인 메시지를 표시한다.

**MVP 정책**

- 하나의 업무에는 담당자를 한 명만 지정할 수 있다.
- 댓글과 파일 첨부는 제공하지 않는다.
- 설명은 일반 텍스트를 기본으로 한다.

### FR-07. 우선순위

**목적:** 중요하거나 긴급한 업무를 쉽게 구분한다.

| 우선순위 | 표시 | 의미               |
| ---- | -- | ---------------- |
| 높음   | 빨강 | 우선 처리가 필요한 업무    |
| 보통   | 주황 | 일반적인 업무          |
| 낮음   | 회색 | 상대적으로 긴급도가 낮은 업무 |

**요구사항**

- 업무 등록 및 수정 시 우선순위를 선택한다.
- 카드에 우선순위를 표시한다.
- 우선순위 기준 필터와 정렬을 지원한다.

### FR-08. 검색·필터

**목적:** 원하는 업무를 빠르게 찾는다.

**검색**

- 업무 제목
- 담당자 이름
- 업무 ID

**필터**

- 업무 상태
- 담당자
- 우선순위
- 완료기한 초과 여부

**요구사항**

- 검색과 필터를 동시에 적용할 수 있다.
- 검색 결과는 보드에서 즉시 갱신한다.
- 필터 초기화 기능을 제공한다.
- 검색 결과가 없으면 안내 메시지를 표시한다.
- 기본 검색 범위는 현재 보드의 미보관 업무로 제한한다.

### FR-09. 내 업무 보기

**목적:** 사용자가 자신에게 배정된 업무를 빠르게 확인한다.

**요구사항**

- 상단에 '내 업무' 메뉴를 제공한다.
- 로그인한 사용자에게 배정된 업무만 표시한다.
- 자신이 참여한 여러 보드의 업무를 통합 조회한다.
- 업무 상태별 조회를 지원한다.
- 완료기한 및 우선순위 정렬을 지원한다.
- 업무 카드를 선택하면 원래 보드의 상세 화면으로 이동한다.
- 보관된 업무와 삭제된 업무는 기본 목록에서 제외한다.

### FR-10. 정렬 기능

**목적:** 업무를 원하는 순서대로 확인한다.

**정렬 기준**

- 사용자 지정 순서
- 완료기한 빠른 순
- 완료기한 늦은 순
- 우선순위 높은 순
- 최근 등록 순
- 최근 수정 순

**정책**

- 기본 정렬은 사용자 지정 순서로 한다.
- 별도 정렬을 적용한 상태에서는 드래그를 통한 순서 변경을 비활성화한다.
- 완료기한이 없는 업무는 완료기한 기준 정렬에서 마지막에 표시한다.
- 정렬 기준은 조회 화면에만 적용하며 저장된 카드 순서를 변경하지 않는다.

### FR-11. 기한 초과 표시

**목적:** 지연된 업무를 쉽게 식별한다.

**요구사항**

- 완료기한이 현재 날짜보다 이전이면 기한 초과로 판단한다.
- Done 상태의 업무는 기한 초과 표시 대상에서 제외한다.
- 기한 초과 업무에는 빨간색 경고 표시를 적용한다.
- 기한 초과 필터를 제공한다.
- 완료기한이 없는 업무는 기한 초과로 판단하지 않는다.
- 날짜 계산에는 서비스 기준 시간대인 Asia/Seoul을 사용한다.

### FR-12. 실시간 동기화

**목적:** 여러 사용자가 동일한 업무 현황을 즉시 공유한다.

**실시간 반영 대상**

- 업무 등록
- 업무 수정
- 업무 삭제 및 복구
- 업무 상태 변경
- 카드 순서 변경
- 담당자 변경
- 우선순위 변경
- 완료기한 변경
- 보관 및 복원

**요구사항**

- 데이터 변경 시 화면을 새로고침하지 않아도 반영한다.
- 다른 사용자에게 변경된 업무 정보가 표시된다.
- 데이터베이스를 변경 사항의 최종 기준으로 사용한다.
- 통신 실패 시 오류 또는 재연결 상태를 표시한다.
- 저장 전 변경 사항과 저장 완료된 상태를 구분한다.
- 동기화 복구 시 최신 데이터를 다시 조회한다.

**성능 목표**

- 정상적인 네트워크 환경에서 변경 완료 후 다른 사용자 화면에 2초 이내 반영되는 것을 목표로 한다.
- 실제 반영 시간은 네트워크 환경에 따라 달라질 수 있다.

### FR-13. 변경 이력

**목적:** 누가 어떤 업무 내용을 변경했는지 추적한다.

**기록 대상**

- 업무 생성
- 업무 제목 및 설명 수정
- 담당자 변경
- 상태 변경
- 우선순위 변경
- 완료기한 변경
- 업무 삭제 및 복구
- 업무 보관 및 복원

**이력 데이터**

- 업무 ID
- 작업 유형
- 변경 항목
- 변경 전 값
- 변경 후 값
- 변경 사용자 ID
- 변경일시

**요구사항**

- 변경 이력을 시간 역순으로 표시한다.
- 업무 상세 화면에 변경 이력 영역을 제공한다.
- 변경 이력은 일반 사용자가 수정하거나 삭제할 수 없다.
- 카드의 단순 순서 변경은 이력 대상에서 제외한다.
- 변경 이력과 업무 수정은 하나의 원자적 처리로 저장한다.

### FR-14. 동시 수정 처리

**목적:** 여러 사용자가 동일한 업무를 동시에 변경할 때 데이터 유실을 방지한다.

**요구사항**

- 각 업무에 수정 버전 번호를 저장한다.
- 사용자가 업무를 수정할 때 현재 버전을 비교한다.
- 버전이 일치하는 경우에만 변경을 저장한다.
- 다른 사용자가 먼저 수정했다면 충돌 안내를 표시한다.
- 충돌 시 사용자가 최신 내용을 다시 확인할 수 있도록 한다.
- 이전 버전을 기반으로 한 변경을 자동 덮어쓰지 않는다.
- 카드 드래그에 의한 상태 변경에도 동일한 충돌 방지 정책을 적용한다.

**MVP 충돌 처리 방식**

1. 사용자 A와 B가 같은 업무를 조회한다.
2. A가 먼저 업무를 수정한다.
3. B가 이전 데이터를 기준으로 저장한다.
4. 서버가 버전 불일치를 감지한다.
5. B에게 '다른 사용자가 먼저 수정했습니다'라는 메시지를 표시한다.
6. 최신 데이터를 조회하고 필요한 경우 다시 수정하도록 안내한다.

카드 순서 변경 역시 다른 사용자의 변경을 무조건 덮어쓰지 않도록 처리한다.

### FR-15. 완료 업무 보관

**목적:** 완료된 업무가 보드에 무한히 쌓이는 것을 방지한다.

**요구사항**

- Done 상태의 업무를 보관할 수 있다.
- 관리자는 완료 업무를 개별 또는 일괄 보관할 수 있다.
- 보관된 업무는 기본 칸반보드에서 제외한다.
- 별도의 보관함에서 조회할 수 있다.
- 보관된 업무의 상세 정보와 이력은 유지한다.
- 보관된 업무는 관리자가 복원할 수 있다.
- 보관함의 업무는 기본적으로 읽기 전용이다.

**정책**

- 자동 보관은 MVP에서 제외한다.
- 완료 업무 보관은 관리자가 수동으로 수행한다.
- 보관된 업무를 복원하면 원래 상태인 Done으로 돌아온다.

### FR-16. 업무 삭제 및 복구

**목적:** 잘못 삭제한 업무를 복구하고 데이터 손실을 방지한다.

**요구사항**

- 관리자는 업무를 삭제할 수 있다.
- 삭제 전 확인 메시지를 표시한다.
- 삭제는 물리 삭제가 아닌 소프트 삭제로 처리한다.
- 삭제된 업무는 기본 화면에서 보이지 않는다.
- 관리자는 휴지통에서 삭제된 업무를 조회할 수 있다.
- 삭제된 업무를 복구할 수 있다.
- 복구 시 삭제 직전의 업무 정보를 유지한다.
- 삭제 및 복구 기록을 변경 이력에 저장한다.

**정책**

- 일반 팀원은 업무를 삭제할 수 없다.
- MVP에서는 영구 삭제 기능을 제공하지 않는다.
- 보드가 삭제 상태일 때는 소속 업무를 개별 복구할 수 없으며 보드부터 복구해야 한다.

- 회원가입 및 비밀번호 재설정

**② 메인 대시보드**

- 내 업무 메뉴
- 업무 검색 및 필터
- 업무 등록 버튼
- 4열 칸반보드
- 카드 드래그 앤 드롭

**③ 업무 상세 화면**

- 업무 제목 및 설명
- 담당자
- 상태
- 우선순위
- 완료기한
- 변경 이력
- 저장 및 취소

**④ 내 업무 화면**

**⑥ 보관함 및 휴지통**

- 완료 업무 조회·복원

### 5.2 주요 사용자 흐름

**신규 업무 등록**

로그인 → 프로젝트 선택 → 업무 등록 → 정보 입력 → 저장 → 칸반보드 표시

**업무 진행 상태 변경**

보드 진입 → 카드 드래그 → 상태 저장 → 다른 사용자 화면 자동 반영

**내 업무 확인**

로그인 → 내 업무 → 상태 및 완료기한 확인 → 업무 상세 조회

**업무 수정**

카드 선택 → 상세 내용 수정 → 저장 → 버전 검증 → 변경 이력 저장 → 실시간 반영

- 사용자 인터페이스의 버튼 숨김뿐 아니라 서버 또는 데이터베이스 보안 규칙에서도 권한을 검증한다.
- 다른 워크스페이스의 데이터는 조회하거나 변경할 수 없다.

## 8. 데이터 구조

데이터베이스는 Firebase Firestore를 기준으로 설계한다.

### 8.1 users — 사용자

| 필드          | 타입        | 설명             |
| ----------- | --------- | -------------- |
| id          | string    | 인증 사용자 고유 ID   |
| email       | string    | 이메일            |
| displayName | string    | 표시 이름          |
| workspaceId | string    | 소속 워크스페이스      |
| role        | string    | admin / member |
| createdAt   | timestamp | 가입일시           |
| updatedAt   | timestamp | 수정일시           |

### 8.2 workspaces — 워크스페이스

| 필드        | 타입        | 설명        |
| --------- | --------- | --------- |
| id        | string    | 워크스페이스 ID |
| name      | string    | 팀 또는 조직명  |
| ownerId   | string    | 생성자 ID    |
| createdAt | timestamp | 생성일시      |
| updatedAt | timestamp | 수정일시      |

### 8.3 boards — 프로젝트 보드

| 필드          | 타입             | 설명        |
| ----------- | -------------- | --------- |
| id          | string         | 보드 ID     |
| workspaceId | string         | 워크스페이스 ID |
| name        | string         | 보드명       |
| description | string         | 설명        |
| memberIds   | array          | 참여 사용자 ID |
| createdBy   | string         | 생성자       |
| deletedAt   | timestamp/null | 삭제일시      |
| createdAt   | timestamp      | 생성일시      |
| updatedAt   | timestamp      | 수정일시      |

### 8.4 tasks — 업무

| 필드          | 타입             | 설명                                |
| ----------- | -------------- | --------------------------------- |
| id          | string         | 업무 ID                             |
| workspaceId | string         | 워크스페이스 ID                         |
| boardId     | string         | 소속 보드 ID                          |
| title       | string         | 업무 제목                             |
| description | string         | 상세 설명                             |
| assigneeId  | string/null    | 담당자                               |
| status      | string         | todo / in_progress / done / issue |
| priority    | string         | high / medium / low               |
| dueDate     | string/null    | 완료기한 YYYY-MM-DD                   |
| position    | number         | 칸반 카드 정렬 위치                       |
| version     | number         | 동시 수정 제어용 버전                      |
| isArchived  | boolean        | 보관 여부                             |
| archivedAt  | timestamp/null | 보관일시                              |
| deletedAt   | timestamp/null | 삭제일시                              |
| createdBy   | string         | 등록자                               |
| createdAt   | timestamp      | 등록일시                              |
| updatedAt   | timestamp      | 수정일시                              |

**설계 원칙**

- 상태, 우선순위는 정해진 값만 허용한다.
- 생성일시 및 수정일시는 서버 기준으로 저장한다.
- 완료기한은 시간대 변환 오류를 줄이기 위해 날짜 문자열로 관리한다.
- 업무 담당자 ID는 해당 보드에 접근 가능한 사용자여야 한다.
- 삭제 및 보관 여부는 별도 필드로 관리한다.

### 8.5 task_history — 변경 이력

| 필드        | 타입          | 설명            |
| --------- | ----------- | ------------- |
| id        | string      | 이력 ID         |
| taskId    | string      | 업무 ID         |
| actorId   | string      | 변경 사용자        |
| action    | string      | 생성·수정·삭제·복구 등 |
| field     | string/null | 변경 필드         |
| oldValue  | any         | 변경 전 값        |
| newValue  | any         | 변경 후 값        |
| createdAt | timestamp   | 변경일시          |

하나의 저장 작업에서 여러 필드가 수정되면 동일한 작업을 구분할 수 있는 변경 ID를 부여할 수 있다.

### 8.6 invitations — 팀원 초대

| 필드          | 타입             | 설명                                     |
| ----------- | -------------- | -------------------------------------- |
| id          | string         | 초대 ID                                  |
| workspaceId | string         | 워크스페이스 ID                              |
| email       | string         | 초대 이메일                                 |
| tokenHash   | string         | 초대 토큰의 해시                              |
| status      | string         | pending / accepted / expired / revoked |
| invitedBy   | string         | 초대한 관리자                                |
| expiresAt   | timestamp      | 만료일시                                   |
| acceptedAt  | timestamp/null | 수락일시                                   |
| createdAt   | timestamp      | 생성일시                                   |

**보안 정책**

- 초대 링크에는 추측하기 어려운 일회용 토큰을 사용한다.
- 원본 토큰 대신 해시를 보관한다.
- 토큰은 만료일 이후 사용할 수 없다.
- 수락 시 로그인 계정 이메일과 초대 이메일을 검증한다.
- 토큰 확인 및 사용 처리는 서버 측에서 수행한다.
- 초대 토큰 원문은 일반 사용자에게 노출되는 DB 문서에 저장하지 않는다.

## 9. 기술 스택

| 영역              | 기술                          |
| --------------- | --------------------------- |
| 프론트엔드           | React                       |
| 언어              | TypeScript                  |
| 빌드              | Vite                        |
| 스타일링            | Tailwind CSS                |
| 인증              | Firebase Authentication     |
| 데이터베이스          | Cloud Firestore             |
| 실시간 동기화         | Firestore Snapshot Listener |
| 서버 측 검증 및 작업 처리 | Firebase Cloud Functions    |
| 배포              | Firebase Hosting            |
| 버전 관리           | Git / GitHub                |

### 기술 구현 원칙

- 가능한 한 단순한 구조를 유지한다.
- Firestore를 단일 데이터 저장소로 사용한다.
- 로그인은 Firebase Authentication을 활용한다.
- 읽기 권한은 Firebase Security Rules로 통제한다.
- 초대 수락, 동시 수정 검증, 변경 이력 기록, 다중 카드 순서 변경처럼 원자적 처리가 필요한 작업은 서버 측에서 수행한다.
- 동시 수정은 Firestore 트랜잭션과 버전 검증으로 처리한다.
- 사용자 입력은 길이 및 허용 값 검증을 적용한다.
- 데이터베이스 보안 규칙과 필요한 복합 인덱스를 배포에 포함한다.

**주의사항:** Firebase 프로젝트 설정, 클라이언트 설정 값, 인증 공급자, 보안 규칙, Cloud Functions 설정이 필요하다. 사용량에 따라 비용이 발생할 수 있으며, 일부 서버 기능은 결제 계정 설정이 필요할 수 있다.

## 10. 비기능 요구사항

### 10.1 성능

- 일반적인 6\~30명 팀에서 원활하게 동작해야 한다.
- 기본 칸반보드는 보드당 활성 업무 300건을 성능 테스트 기준으로 삼는다.
- 정상적인 환경에서 보드 초기 로딩은 3초 이내를 목표로 한다.
- 실시간 동기화는 변경 완료 후 2초 이내 반영을 목표로 한다.
- 불필요한 중복 데이터 조회를 최소화한다.

### 10.2 안정성

- 데이터 저장 실패 시 사용자에게 안내한다.
- 동기화 실패 시 재연결 상태를 표시한다.
- 저장 실패한 드래그 결과를 성공한 것처럼 유지하지 않는다.
- 브라우저 새로고침 후에도 저장된 데이터를 유지한다.
- 충돌 발생 시 사용자에게 알리지 않고 기존 값을 덮어쓰지 않는다.

### 10.3 보안

- 인증되지 않은 사용자의 업무 데이터 접근을 차단한다.
- 워크스페이스 및 보드별 접근 권한을 검증한다.
- 서버 측 권한 검증을 우회할 수 없어야 한다.
- 다른 사용자의 인증 정보를 노출하지 않는다.
- 업무 설명은 안전하게 렌더링하여 스크립트 삽입을 방지한다.
- 저장된 비밀번호는 직접 관리하지 않고 인증 서비스를 활용한다.

### 10.4 반응형

- 모바일 390px
- 태블릿 768px
- PC 1280px

세 환경에서 주요 기능을 사용할 수 있어야 한다.

### 10.5 접근성

- 입력 항목에는 명확한 레이블을 제공한다.
- 색상만으로 업무 상태나 중요도를 전달하지 않는다.
- 키보드로 주요 기능을 사용할 수 있어야 한다.
- 충분한 색상 대비와 터치 영역을 확보한다.

## 12. 완료 및 검수 기준

### AC-01. 사용자 인증

- 회원가입과 로그인이 정상 동작한다.
- 로그아웃이 정상 동작한다.
- 로그인하지 않은 사용자는 내부 데이터에 접근할 수 없다.

### AC-02. 팀원 초대

- 관리자가 초대 링크를 생성할 수 있다.
- 유효한 초대 대상만 팀에 참여할 수 있다.
- 만료되거나 취소된 링크는 사용할 수 없다.

### AC-03. 보드 관리

- 관리자가 보드를 생성, 수정, 삭제 및 복구할 수 있다.
- 일반 팀원은 참여한 보드만 조회할 수 있다.
- 다른 워크스페이스의 보드에 접근할 수 없다.

### AC-04. 업무 관리

- 업무 등록 및 수정이 정상 동작한다.
- 제목, 설명, 담당자, 기한, 우선순위, 상태가 저장된다.
- 업무 수정 후 새로고침해도 변경 사항이 유지된다.
- 업무 상세 화면에서 변경 이력을 확인할 수 있다.

### AC-05. 칸반 기능

- 카드의 열 간 이동이 정상 동작한다.
- 동일 열에서 순서를 변경할 수 있다.
- 변경한 상태와 순서가 저장된다.
- 저장 실패 시 이전 상태로 복구된다.

### AC-06. 실시간 동기화

- 두 명의 사용자가 같은 보드를 동시에 열 수 있다.
- 한 사용자가 카드를 이동하면 다른 사용자 화면에 새로고침 없이 반영된다.
- 업무 생성, 수정, 삭제 및 복원도 동기화된다.
- 연결이 끊긴 경우 상태를 안내하고 재연결 후 최신 정보를 반영한다.

### AC-07. 동시 수정

- 동일한 버전에서 두 사용자가 동시에 수정했을 때 두 번째 수정은 충돌로 처리된다.
- 충돌 발생 시 최신 내용을 확인할 수 있다.
- 먼저 저장된 내용이 예고 없이 덮어써지지 않는다.
- 업무 수정과 변경 이력이 함께 정상 저장된다.

### AC-08. 조회 기능

- 업무명 및 담당자 검색이 동작한다.
- 상태, 담당자, 우선순위 필터가 동작한다.
- 정렬이 정상 동작한다.
- 내 업무에서 사용자에게 배정된 업무만 조회된다.
- 기한 초과된 미완료 업무가 정확하게 표시된다.

### AC-09. 보관·삭제·복구

- Done 상태의 업무를 보관할 수 있다.
- 보관한 업무는 기본 보드에서 사라진다.
- 보관함에서 업무를 복원할 수 있다.
- 삭제한 업무는 휴지통에서 복구할 수 있다.
- 일반 팀원은 삭제 및 복구 권한이 없다.

### AC-10. 반응형 및 배포

- 390px, 768px, 1280px에서 핵심 기능을 사용할 수 있다.
- 모바일에서 카드 상태를 변경할 수 있다.
- 레이아웃이 깨지지 않는다.
- 공개된 서비스 URL로 로그인 화면에 접근할 수 있다.
- 인증 및 권한이 없는 사용자는 내부 업무 데이터를 조회할 수 없다.

| 항목       | 적용한 정책                    |

개발 시 특히 중요한 부분은 카드 순서 변경과 동시 수정 처리입니다. 두 명이 동시에 카드를 드래그하면 순서가 꼬일 수 있으므로, 실제 구현에서는 보드 또는 상태 열 단위의 순서 버전 관리, 트랜잭션, 실패 시 재조회 정책까지 구체화해야 합니다.

또한 Firestore 데이터 모델은 현재 논리적 구조를 정리한 단계입니다. 구현 시 컬렉션 경로, 보드 멤버십 검증, 변경 이력 트랜잭션, 조회 인덱스를 확정해야 합니다.
